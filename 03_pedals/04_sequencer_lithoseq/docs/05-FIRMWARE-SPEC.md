# 05 — Прошивка: структура, метрики, плейхед, маппинг

## 1. Слои и переносимость

```
core/      — чистый C, без HAL: пайплайн, метрики, плейхед, маппинг,
             квантайзер, пресеты. Компилируется и на ПК (тесты!).
hal/       — камера (DCMI+DMA), I2C DAC, USB (CDC+MIDI), flash-конфиг.
app/       — склейка: планировщик, CLI, протокол отладки.
tools/     — ПК: просмотрщик карты (Python), генератор тестовых карт,
             golden-тесты core на референсных кадрах.
```

Правило: **core не знает про железо**. Вход core — готовая карта 32×32
(uint8) + тики клока; выход — события нот/CV. Это даёт (а) перенос в модуль
фазы 4 без изменений, (б) unit-тесты метрик и маппинга на ПК на записанных
кадрах — детерминизм проверяется побайтово (golden files).

Арифметика: только целочисленная / фиксированная точка (Q15). Ни float
в core, ни RNG (D7). «Случайность», если понадобится, — xorshift от
CRC32 карты: одна и та же пластина даёт одну и ту же «случайность».

## 2. Пайплайн кадра

0. Контроллер освещения выставляет свет по активному режиму (TRANS /
   REFLECT-D — один кадр; REFLECT-4 — цикл N→E→S→W из 4 кадров, свод
   max−min и avg в hal-слое; core получает уже единый «сырой» кадр).
1. DCMI → двойной буфер QVGA Y-канала.
2. ROI (из конфига) → box-усреднение блоками → raw32[1024].
3. Калибровка: map[i] = clamp8((raw[i] − dark[i]) · gain[i] >> SHIFT).
4. Пирамида: map16, map8 усреднением 2×2.
5. Метрики (§3) → структура `frame_features`.
6. Атомарная подмена указателя активного кадра для плейхеда (между тиками).

## 3. Метрики (детерминированные, фикс-пойнт)

**D — локальная плотность.** D(x,y) = среднее окна 5×5 на map32 (края —
клампинг координат). Хранится как D-карта 32×32.

**S — локальная резкость.** S(x,y) = средний |лапласиан| в окне 5×5:
L(x,y) = |4·m(x,y) − m(x±1,y) − m(x,y±1)|, усреднённый по окну.
Дешевле и стабильнее оконного DCT; смысл тот же: «зернистость/края».

**R — глобальная поворотная симметрия.** Для map32 считаются нормированные
корреляции: r90 = corr(map, rot90(map)), r180, rmir (зеркало). 
R = max(r90, r180, rmir), клампится в [0..1] (Q15). Считается на map16,
если на map32 не влезает в бюджет кадра (влезает с запасом, но правило
зафиксировано).

**G — градиент вдоль траектории.** G(t) = |map32[p(t)] − map32[p(t−1)]|.
Считается в плейхеде, не в кадре.

Нормировка выходов метрик — **фиксированными** константами шкалы,
подобранными один раз на PATTERN-SET (08, T-M1), не по текущему кадру (D6).
Допускается опциональная «музыкальная» кривая (гамма/таблица) на метрику —
часть пресета, не адаптация.

## 4. Плейхед

Интерфейс генератора траекторий: `next(traj_state) -> (x, y)` на тик клока.
Реализации v1: растр, бустрофедон, спираль-внутрь, спираль-наружу,
радиальные лучи (8 спиц). Параметры: длина шага, декс/номер спицы,
направление. Заложенный интерфейс (не реализуется в v1): `seek(x, y)` для
будущей X/Y CV-адресации и аудиоскоростного обхода.

Клок: внутренний таймер (BPM из CLI) или внешний тик (USB-команда в v1).

## 5. Маппинг и пресеты

На каждый тик из позиции p: d = D[p], s = S[p], g = G, плюс глобальный R.

```
нота:    degree = d * n_степеней >> 8
         scale_mask = SCALES[ level(R) ]      ← ядро D8
         note = quantize(degree, scale_mask, root, octaves)
gate:    гистерезис по G: on при G > T_hi, off при G < T_lo;
         в Compose — длительность/пропуск по сетке (см. ниже)
accent:  s > T_acc → velocity high / aux CV пик
CV aux1: s (тембр), CV aux2: R (медленный, «характер образца»)
```

Таблица шкал по уровню симметрии (5 уровней R):
R высокий → обертоновый ряд / мажорная пентатоника → диатоника → 
минорная гармоническая → хроматика → микрокластер (интервалы < полутона
через pitch bend в MIDI-фазе, прямым CV — в фазе 3).

**Пресеты — наборы коэффициентов, не ветки кода:**
- **Reveal**: кривые метрик линейные, scale_mask от R обновляется плавно,
  ритм — чистый G-гистерезис. Образец «звучит как есть».
- **Compose**: R дополнительно управляет регуляризацией ритма (гейты
  притягиваются к сетке 1/8–1/16 с силой ∝ R), степень квантования питча
  жёстче, s управляет плотностью пропусков нот. Алгоритм «трактует» форму.

Требование F11: пресеты обязаны быть слепо различимы (T-M2).

## 6. Протокол отладки (USB CDC)

Бинарные пакеты `[0xA5][type][len][payload][crc8]`:
`0x01` map32 (1024 Б), `0x02` frame_features, `0x03` события нот,
`0x04` состояние плейхеда. Текстовый CLI поверх того же порта (строки,
начинающиеся не с 0xA5): `cal dark|white`, `mode trans|refd|ref4`,
`roi …`, `traj …`, `preset …`, `bpm …`, `dump`, `save`. ПК-просмотрщик: Python + pyserial + matplotlib/
pygame; отображает карту, позицию плейхеда, метрики, пианоролл событий.

## 7. Бюджет производительности (H743, 480 МГц — всё с огромным запасом)

| Операция | Оценка |
|---|---|
| Даунсемплинг 200×200→32×32 | ~40k MAC — микросекунды |
| D, S карты | ~50k оп. |
| R (3 корреляции 32×32) | ~9k MAC |
| Итого на кадр при 15 fps | ≪ 1% CPU |

Узкое место проекта — не вычисления, а оптика/механика (см. DESIGN-OPINION).

## 8. Тестирование core

- Golden-тесты: записанные кадры PATTERN-SET → эталонные map/метрики/
  события; CI на ПК сравнивает побайтово.
- Свойства: инвариантность R к повороту миры; монотонность D по плотности
  точек; нулевые gates на BLANK.
